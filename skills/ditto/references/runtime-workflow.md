# Mobile-control runtime workflow

All agent-facing UI operation and capture for an Android Flutter phase goes through the mobile-control MCP. The server may use Android platform tooling internally. Ditto accepts evidence only through the recorded MCP server, tool, session, target, and receipt.

## Establish the session

Use the emulator or authorized test device named by `runtime_target`. The preflight probe exercises launch, tap, type, swipe, back, screenshot, and hierarchy commands and returns device/environment facts. Input-command success only proves the transport; observe meaningful app outcomes during phase replay. Record viewport pixels, density, OS/API, locale, theme, font scale, orientation, renderer when relevant, and package identity.

One integration owner controls a device session. Parallel agents can inspect package evidence or implement isolated components, but they do not share or independently drive that session. Re-probe after device replacement or controller restart. New capture sessions read the current environment, and each checkpoint rejects changes within that session. Previously retained evidence keeps its historical session identity.

## Collect the original pack once

Before handing control to a human, prepare each checkpoint’s fixture, setup/actions, and `capture_when`: the exact visible state to capture, including when to wait for settling. Add `expect` when a unique screen marker is available. The recorder shows these contract fields; do not maintain separate human instructions. Older contracts remain readable with setup as the displayed fallback, but prepare an actual capture condition for new recording work. Prepare each named fixture, execute the contract setup and actions in checkpoint order, and export exactly the declared PNG, XML, trace, state, network, and semantics files. Use `<order>_<checkpoint-id>.<kind>` names plus `capture.json`. Stop the sequence when an action or expected UI target fails; never label the resulting state successful. Declare only artifact kinds supported by the current controller.

The original pack is complete only when every declared artifact exists, hashes match, controller identity matches active preflight, reverse MCP exports match the original package, and the manifest binds all facts. Freeze after reviewing scope unknowns and evidence completeness.

The AI may inspect any file in the phase and may query the running original again when evidence is missing or contradictory. After freeze, use `phase collect-original --checkpoint <id>` with a fresh controller export for each selected checkpoint. This creates a new original manifest, keeps unchanged evidence by hash, and reopens affected clone comparisons. A changed checkpoint definition belongs in a new contract revision. If only setup wording changes or previously recorded app action labels are identified as incidental system actions, use `phase rebind-original` before clone collection; it retains the original pixels and trace and records both protocols. Changed fixtures, checkpoint identity, artifact requirements, or new actions require real recapture.

## Implement and capture the clone

Implement the complete bounded phase before final replay. For Dart layout edits, `flutter run` on the intended Android emulator and hot reload the running app. After Flutter launches it, use mobile-control `preview_begin` for UI actions and `observe_screen`/`inspect_ui` for feedback. Preview does not install an APK or create receipts; `capture`, `run_checkpoints`, and `finalize` are unavailable in that mode. End it with `abort` and stop the Flutter run session before evidence capture. Hot reload preserves state, so use a restart when the changed behavior depends on startup or persisted state. A seeded screen entry can shorten preview navigation; it cannot replace real route execution for final behavioral evidence. Replays execute actions, not instantly restore app state. Reuse existing date/input injection seams for deterministic fixtures before adding libraries or changing the device clock. A browser preview is optional for an already web-compatible screen; it cannot establish Android parity.

Build one identified debug clone APK and let mobile-control verify installation, skipping reinstall only when the installed package is verified identical. Restore equivalent fixtures and repeat the frozen original protocol. Keep the same target and environment. Export the exact declared files and controller receipt. Never submit a preview screenshot or hot-reloaded process as evidence for an APK hash.

Each clone checkpoint records the APK SHA-256 and manifest revision. A later build does not erase earlier evidence. After dependency invalidation or a revised oracle, export only the files for reopened checkpoints. The controller capture must identify the installed APK hash, fixture, setup/actions, and capture time. The next clone manifest and comparison cover those checkpoints; unaffected verdicts retain their earlier result and exact build identity.

## Efficient control

Use the phase contract and original manifest to define the replay protocol; retain executable steps in the controller export instead of reconstructing navigation every run. `inspect_ui` returns bounded visible labels, IDs, and bounds; use `tap_target` when those labels are stable. It already waits up to `target_timeout_ms` (default 5000, maximum 30000), then taps the resolved target once; do not precede it with `wait_target` for the same selector. Reserve `wait_target` for observing a state without tapping. Use `observe_screen` only when an image is needed. `perform` records action arguments; label each declared action with its exact `step` text. `replay(steps=[...])` batches up to 100 actions. `run_checkpoints(plan=[...])` batches replay, a bounded wait for an optional expected UI target, and capture per checkpoint; it stops at the first mismatch and preserves earlier completed checkpoints. For each transition, set `expect` to a unique marker on the resulting screen and adjust `expect_timeout_ms` only if needed (default 5000, maximum 30000). A shared button label such as `Next` cannot establish which screen is visible. When no distinct UI target is exposed, observe the screen before capture rather than running an unguarded batch. Supply a concrete `observed_state` for each checkpoint and inspect the captured PNG/XML before accepting it. Setup/fixture labels describe intended preparation; they do not themselves prove it ran.

Use the local recorder immediately when a human is available and prefers to navigate the original; otherwise proceed autonomously. For either original or clone navigation, stop after at most two targeted failed attempts and offer takeover. If nobody is available, report the specific blocked checkpoint, retain completed work, and continue independent work where possible; do not retry indefinitely.

Start the recorder after package-bound `begin` and give its localhost URL to the human; see [commands](commands.md) for calls and checkpoint selection. The panel follows the declared action order and automatically names evidence. Hand over the active session only when pending labeled actions are a correct prefix of the next checkpoint and the UI is still in the intended state. The human can select Return control to AI, which freezes panel input; check recorder status and stop the recorder before resuming AI control. Stopping preserves the active session and completed captures; only one controller drives the device at a time. If the pending protocol is invalid, preserve completed exported evidence before aborting and restore the fixture in a fresh session. Do not use unrecorded ADB/manual clicks. Human navigation and takeover collect evidence or recover execution; they are not mid-phase approval.

The export includes a replay candidate with recorded action arguments and checkpoint fields. Add a unique expected-screen selector when available; missing markers require review before batch execution. Review fixtures, selectors, incidental actions, and screen expectations before reuse, especially between original and clone. A successful original recording does not verify clone navigation. Validate the reviewed route on the clone and inspect its resulting screenshots/XML before accepting its behavior. Prefer stable selectors and explicit screen expectations over coordinate taps and fixed sleeps; screens without usable markers need individual visual inspection instead of an unguarded batch.

Use explicit `reset` only for a fixture that calls for clearing app data; `stop`, `launch`, and `restart` support lifecycle checks. Unicode text entry, traffic capture, and Flutter semantics have no backend yet; identify these limits during preparation. A fixture requiring an unavailable capability blocks that checkpoint. `abort` discards an incomplete capture and releases the device. Finalize releases it after saving. After an emulator restart within the same MCP process, restart the AVD and call `recover`; it checks device, package, and environment, retains completed captures, and requires replaying navigation to the failed checkpoint. A server process restart requires a new capture session. Capture one deterministic settled state per checkpoint. Batch checkpoints in one controlled session while resetting fixtures exactly where the contract requires it.

Do not ask for human review or approval during collection, implementation, or correction; recorder handoffs on either app are optional navigation assistance. Run the automated readiness gate after all required semantic verdicts close. Commit the ready implementation and tracked phase records, then present the identified build, overview, full triptychs, report, accepted differences, proposals, and gaps for one end-of-phase decision.
