Browser-free handoff (observed 2026-10-28): a Python `requests` client with no browser cookies authenticated through `POST /identity/ext-login`, called the dashboard and requested a handoff ticket through `POST /esanchit/esanchitDynamicUrl`. It followed the ticket over HTTPS only: 302 to `http://www.icegate.gov.in/esanchit/?...` → rewrite to HTTPS → 302 to `http://www.icegate.gov.in/esanchit/home` and set `JSESSIONID` → rewrite to HTTPS → 200 with the upload form. The dashboard token lasted exactly 10 minutes; `POST /identity/refresh-token` issued a new 10-minute token only before expiry. A 35-minute keepalive with a refresh every 5 minutes stayed authenticated and reopened eSANCHIT at the end; no 30-minute cap was observed. Handoffs at t0, +4, +8 and +12 minutes worked and failed at +16/+20 after expiry. After 12 minutes with no eSANCHIT requests, `/esanchit/home` returned 500, consistent with the FAQ's ~10-minute timeout. Each handoff returns a new ticket and appears to create a new eSANCHIT session; the old `JSESSIONID` was not reusable after expiry. Never log the handoff URL: it contains a bearer `DM_TICKET`. In these tests the `ext-login` token was accepted by the dashboard and handoff before any OTP call, including fresh logins up to 78 minutes after the last verified OTP; this may be an account-level 2FA window, not proof that OTP is optional, the user later requested removing the client OTP fallback.

Current authentication hypothesis: assume upload requires an authenticated session. The successful submission used session cookies, but we did not isolate the account-identifying cookie or field, nor test an unauthenticated submission; the uncredentialed GET alone does not prove rejection. Existing cookies can be reused only while the server accepts the session, and the active dashboard has renewed eSANCHIT access without another OTP. No durable account API key has been identified; the dashboard refresh-token endpoint is session-bound and cannot revive an expired token. Restart persistence was not isolated (the one restart observation was confounded by age), and the server's absolute session cap was not observed through 35 minutes. Saved credentials cannot guarantee avoidance of future login or OTP. Keep any session secrets private and out of the repository.

Signature validation 2026-10-28: verifying with pyHanko (and independently with `openssl cms -verify`) showed that `~/Documents/e-sanchit-uploader/input/Registration-cum Membership Certificate.pdf` is **not** genuinely signed. Its single `adbe.pkcs7.detached` signature covers the whole file, the byte-range digest matches, but the RSA signature value itself fails: pyHanko reports `intact=True, valid=False`, OpenSSL reports `bad signature`, `CMS Verification failure`. The signer certificate is an Indian DSC (Rajesh Singh, DGFT IEC-0500013870) valid 2025-04-24 to 2027-04-24, so the file was signed once and then altered, or the signing step was interrupted. An earlier marker-based heuristic (presence of `/ByteRange` plus `/SubFilter`) classified this file as "signed"; do not trust marker heuristics. Re-sign it before any upload: a submission would fail the portal's `digiSignValidated` check, and a failed submission may still leave a DRN behind. By contrast `~/Documents/smart-gmail/E_SANCHIT_1196_signed_.pdf` validates fully: four signatures, `intact=True`, `crypto_valid=True`, `trusted=False` because Indian DSCs do not chain to `certifi`; untrusted is the normal verdict and is not a failure.

Upload limits, researched 2026-10-28 against four sources. The published numbers disagree and the live page is the only one that matches current behaviour:

- ICEGATE FAQ (`/help/faq`): "At one-time maximum 5 documents can be uploaded each of size 1 MB" and "Only PDF format is accepted in e-SANCHIT application having size lesser than 1 MB". Also states "Five IRN numbers can have one DRN" and "A group of IRN should be entered into the Bill of Entry, not DRN".
- eSANCHIT step-by-step PDF (2022-04, https://www.icegate.gov.in/sites/default/files/2022-04/eSANCHIT_Step_by_Step_Procedure_updated.pdf): 1 MB per file, "maximum 5 documents" per batch.
- Upload dialog text on the live page: "Maximum size per file is 2 MB.", "The total number of maximum files are 5 per DRN.", "Each file should have a unique name.", "File Upload will be successful only if digital signature is verified successfully.", and formats PDF/Doc/Docx/jpg/jpeg.
- The page's own JavaScript: `maxSize = parseInt('2097152')` per file, and a per-request cap of 10,485,760 bytes for a broker (`user='OTHERS'`) account versus 52,428,800 for agency users. Both branches print the message "Maximum of 50 MB is allowed per request.", so the visible 50 MB is wrong for broker accounts by a factor of five.

Two consequences. Five files at 2 MiB already reach the 10 MiB per-request ceiling, so the total cap is the practical batch limit even though the dialog talks about a file count. And the five-file rule is not enforced client-side at all: `numberOfFileCheck()` compares the selection against `documentBean.maxFile`, which the server never substitutes, leaving `maxFiles` bound to the jQuery function `$` (ASI makes the statement legal), so the comparison is always false and the "max 5 files per DRN" alert cannot fire. Whether the server enforces five is unproven; treat it as advisory and do not build a workflow that depends on uploading more than five. The client therefore uses 2 MiB per file, 5 files per DRN and the live per-request cap, re-read from the page after every handoff, with `--strict-limits` to turn warnings into errors.
